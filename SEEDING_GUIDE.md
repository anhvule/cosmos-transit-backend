# Per-Ascendant Description Seeding Guide

This guide tells another agent (or you, in a future session) how to fill in
the per-ascendant event descriptions for a new native — given their birth
data, you produce ~530 chart-specific descriptions across one or more
event-database categories (career / relationship / investment / advice / food
/ gain / loss / engineering / network / galactic).

Each description is a focused Vedic interpretation, written from a specific
**lens** (career, food, advice, etc.), tuned to the native's actual natal
chart so the output is meaningful for that person rather than generic.

---

## 1. Inputs you need

A native's birth data:

```json
{
  "name": "...",
  "birthDate": "YYYY-MM-DD",
  "birthTime": "HH:mm",
  "latitude":  16.0427,
  "longitude": 120.7946,
  "timezone":  8
}
```

Plus the **lens** to write from (one or more):
- **career** — promotion, layoff, projects, contracts, boss, colleagues
- **relationship** — partner, marriage, romance, social bonds
- **investment** — speculation, finance, equity, gains
- **gain** / **loss** — sudden gain / sudden loss days
- **advice** — daily-navigation, what to do/avoid today
- **food** — diet, eating, digestion, Ayurvedic guidance

## 2. Compute the natal chart

Run the kerykeion bridge to get sidereal Lahiri positions:

```bash
echo '{"birthDate":"1991-09-13","birthTime":"15:30","latitude":16.0427,
       "longitude":120.7946,"timezone":"Etc/GMT-8","transitDate":"2026-04-29"}' \
  | python3 services/astrology_kerykeion.py --json \
  | python3 -c "import sys, json; d=json.loads(sys.stdin.read()); \
                [print(p['name'], 'sign='+p.get('sign','?'), 'house='+str(p.get('house','?'))) \
                 for p in d.get('natalPlanets',[])]"
```

Note timezone: an integer like `8` becomes `Etc/GMT-8` (signs are inverted by
the POSIX convention; UTC+8 → `Etc/GMT-8`).

You'll get something like:

```
Ascendant     sign=Capricorn       house=1
Sun           sign=Leo             house=8
Moon          sign=Libra           house=10
Mercury       sign=Leo             house=8
Venus         sign=Cancer          house=7
Mars          sign=Virgo           house=9
Jupiter       sign=Leo             house=8
Saturn        sign=Capricorn       house=1
Rahu          sign=Sagittarius     house=12
Ketu          sign=Gemini          house=6
```

Capture: `ascendant_sign`, plus each of the 9 planets' (sign, house).

## 3. Generate the empty seed file (if not already present)

The empty per-user seed files are auto-generated by
[`_generate_user_seeds.js`](db/_generate_user_seeds.js) (which was the
generator I used; it was deleted after producing the 7 seed files). If a
file is missing, regenerate it. The generator must be parameterized with
the native's natal chart.

The empty seed exposes 530 events organized into 6 buckets (counts may
vary slightly; the rulers/dispositors counts depend on the natal chart):

| Bucket | Count | What it covers |
|---|---:|---|
| **Rulers** | 12 | The lord of each house (per ascendant) placed at its natal house |
| **Dispositors** | ~6 | Sign-lord of each natal planet's sign, placed at lord's house, deduped |
| **Transits** | 108 | Each of 9 planets through each of 12 houses |
| **Angle aspects** | 72 | 9 planets × {ASC, MC} × 4 phase variants |
| **Outer specials** | 8 | Pluto-Saturn and Uranus-Venus, × 4 phase variants |
| **Aspects** | 324 | 9 transit × 9 natal planets × 4 phases (natal house fixed) |

All other (~3,800) per-ascendant rows in the DB are events that **cannot
fire** for this chart given the natal placements — leave them empty.

## 4. Authoring conventions

**Tone**

- Direct, actionable, second person.
- Never use astrology-jargon preambles (do not write "Mars-MC aspect
  exact —" or similar). The user reads pure guidance.
- ~80–200 words per description; tighter for aspects (high volume),
  fuller for rulers/dispositors (high leverage).
- Reference the natal placement explicitly when relevant — e.g. for a
  Capricorn-asc Saturn-in-1st native, food advice can mention Vata-dominant
  body, slow digestion, traditional warm cooked food. The interpretation
  must be recognizably *theirs*, not a horoscope-app generic.

**Lens-specific framing**

| Lens | Framing |
|---|---|
| career | boss, promotion, layoff, project, contract, colleague, status |
| relationship | partner, romance, social bond, public-face dynamics |
| investment | risk, speculation, equity events, gains, advisory |
| advice | what to do today, what to avoid today, navigation |
| food | what to eat, what to avoid, digestion, Ayurvedic dosha |
| gain | sudden gains, windfalls, opportunity windows |
| loss | sudden losses, risk windows, what to protect |

**Phase variants**

Each aspect has 4 phase strings:
- *(no phase)* — the broad window; describe overall meaning
- `: Starts` — rising / approaching; what to prepare
- `: Exact` — peak day; what to do *today*
- `: Ends` — separating / fading; what to lock in

## 5. Filling the seed file

The seed file is an array of `{ name, description }` objects. Edit the
file directly — replace each empty `description: ''` with your authored
text. Single-quoted strings; escape any embedded `'` as `\'`. Once saved,
run `node db/seed_<area>_<ascendant>.js` to push fills into the DB.

Empty descriptions are **skipped** by the seed runner, so partial fills
are safe. Re-running the seed overwrites whatever is in the file at the
matching name with the latest text.

**Workflow**

```bash
# 1. Edit
$EDITOR db/seed_career_capricorn.js

# 2. Run
node db/seed_career_capricorn.js
# → "[Capricorn career] N updated · M still empty · 0 not in DB"

# 3. Verify firable coverage
node -e "<inline coverage check; see existing examples in conversation history>"
```

## 7. Coverage check

After seeding, verify:

```bash
sqlite3 db/<area>_events.db "SELECT COUNT(*) FROM events WHERE ascendant='<Ascendant>' AND description != '';"
```

Should equal the number of firable events filled (target ~530 for full
coverage of one lens). The remaining ~3,800 empty rows for that ascendant
are non-firable templates and stay empty by design.

## 8. After fill — runtime check

Hit the live API and confirm interpretations land:

```bash
curl -s -X POST http://localhost:3000/api/career \
  -H 'Content-Type: application/json' \
  -d '{"name":"...","birthDate":"...","birthTime":"...","latitude":"...",
       "longitude":"...","timezone":8,"transitDate":"<today>"}' | jq .
```

Every `aspects[].interpretation` and `rulers[].interpretation` should be
non-empty for a chart whose ascendant is fully seeded.

## 10. Cost-saving tips for the next agent

- Aspects (324 per lens) are the long tail. Use tighter ~50–80 word
  descriptions for these; reserve fuller text for rulers/dispositors.
- The phase variants share semantic spine; vary the verbs / focus
  but don't reinvent the meaning each time.
- Group by transit planet (Jupiter aspects → Ketu aspects → ...) and
  do all 36 of one planet in a single Edit call. The file is sorted
  alphabetically by transit planet then natal planet — match that
  order so old/new strings line up cleanly.
- Always verify with `node db/seed_<area>_<asc>.js` after each
  major Edit; the count `N updated · M still empty` tells you exactly
  what's left.
